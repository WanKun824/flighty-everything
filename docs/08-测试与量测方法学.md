## 8.2 实拍量测方法学（改「手感」类参数的必读）

这个项目改过好几轮「大小 / 抖动 / 平滑」这类**视觉参数**，只靠截图对比是不可靠的 ——
不同轮次的光照、帧率、画质、缩放都会污染比较。沉淀下来的方法（散落在 `HANDOFF-20260814.md`、
`page.tsx` 注释和本会话的量测脚本里）：

### 前提（已存 memory）

- Playwright 用绝对导入路径：`file:///C:/Users/v_wkunnwan/AppData/Roaming/npm/node_modules/@playwright/test/node_modules/playwright/index.mjs`。
- 浏览器参数：`--use-gl=angle --enable-unsafe-swiftshader`（SwiftShader 软件渲染）。
- **必须先点「探索」按钮**（`page.getByRole("button", { name: "探索" }).click()`），
  等 `.map-rider canvas` 出现（`waitForSelector(…, { timeout: 90000 })`）。
- dev server 在 **3001**（`http://localhost:3001/`），不是 3000。

### 量尺选择

| 要量的东西 | 量法 | 为什么 |
| --- | --- | --- |
| 载具像素尺寸 / 宽度 | `getBoundingClientRect()` + 读 `--rider-zoom`；或红面罩 PCA 次/主轴比 | hero 机位仰角 24°，次轴九成来自高度、宽度只占 ~7%，13% 的变窄摊进去就剩 1%，掉进帧间噪声 —— 改到 **map 机位（仰角 50°）** 量 |
| 抖动（逐帧偏航） | **页面内挂 rAF 采样器**：每帧把载具 WebGL 画布 `drawImage` 进 2D 画布，原地算红面罩 PCA 主轴角，攒够帧一次带回 | 逐张 screenshot 一张要一两百毫秒且间隔不均，二阶差分算出来全是采样抖动不是画面抖动 |
| 帧率可比性 | **固定时间窗 + 均匀 60Hz 重采样**再差分 | SwiftShader 帧率在 28~59Hz 之间飘，按帧数收会让两轮采到长度不同的路段；差分算子对 Δt 极敏感，丢一帧就凭空多出一个大二阶差分 |
| 手势是否真的进到地图 | `elementFromPoint` 找一个压在 canvas 上的点再点 | 滚轮被 Playwright 当触控板（六下只推 0.44 级）、双击落点被右侧面板盖住 —— 用 Mapbox 键盘缩放（`Equal` 键，每按正好 +1 级）代替滚轮 |
| 载具尺寸的缩放阶梯 | 键盘逐级放大读 `--rider-zoom` 与实际像素 | 真实缩放按「起点 + 按键次数」算；反解 zoomFactor 那一路只在变化 >4% 时才发布，读数滞后最多 0.19 级 |

### 操作纪律（踩过的坑）

1. **暂停再量**：逐张量尺寸前先暂停动画、跳到段起点（progress 是确定值），否则两轮航向
   不同、投影没法比。
2. **固定时间窗**：`IDLE 2500ms`（噪声底：暂停段只有量具噪声 + 待机呼吸）+ `RUN 7000ms`
   （行驶段）。**必须同时采两段** —— 只采行驶段会把量具噪声当成抖动。
3. **量具端放大被测物**（如 `--rider-zoom: 3`）给红面罩更多像素，PCA 噪声按 1/√N 降；
   动力学与元素尺寸无关，放大不影响被测量。
4. **注释里的数字必须是实测值**。这个项目出现过两次把预测值当实测值写进注释 ——
   都在 review 时被发现并替换成真实量测。写任何「峰值/RMS/像素」进代码注释前，
   要么有仿真输出、要么有实拍输出，二者都没有就不要写具体数字。
5. 量 A/B 两轮时：同一段路线（22km 公路）、同一窗口、同一直方图指标
   （角速度峰值 / 角加速度 RMS / 变向次数），跑两轮交叉验证。

### 仿真作为前置

参数空间太大时先建最小仿真（如 `page.tsx` 516–527 行 HEADING_SMOOTH 的 S 形公路模型：
4km、10m 顶点、σ≈10.8°/顶点 的 bearing 噪声），拿到「改参数 → 指标变化」的预测，
再用实拍复核。预测-实拍对得上的示例见文档 2 §2.5。
